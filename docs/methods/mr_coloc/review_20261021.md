## 首次审查发现（以下四项已闭环，保留原始证据）

1. **[P1] 缓存命中未核当前请求的仓库与固定提交。** `method_library.py:211-218` 在已有 `source_acquired` receipt 时仅核文件完整性即返回；`fetch_code_subset:283-289` 对完整/子集缓存也一样。`verify_source:170-197` 没有比对传入 source、receipt、文件 manifest 的 repository/commit。临时行为复现：缓存存 `old/repo`、SHA=`111...111`，调用同一 source ID 的 `new/repo`、pinned_commit=`222...222`，仍返回旧仓库/旧 SHA，`verify_source` 返回 verified，且无需联网。更新 pin 或修正 repo 后会静默给错版本。建议缓存命中先比较规范仓库/固定提交与 manifest/receipt，发现不一致保留旧文件并明确拒绝，或按版本分缓存；不能仅靠内容哈希判身份一致。

2. **[P2] `fetch_source` 直接调用允许 `.`/`..` 作为 source ID。** `method_library.py:202` 的 `[A-Za-z0-9_.-]+` 与 registry、subset 函数采用的严格 ID 规则不同。临时复现 `fetch_source({'id':'..','repository':'valid/repo'}, cache)`，模拟 API 失败后在 cache 父目录实际写出 `receipt.json`。CLI 先运行 `validate_registry` 能挡住此输入，因此现有规范 registry 不受该示例触发；公共函数自身仍不满足缓存边界。建议统一安全 ID 规则，并确认 resolved source_dir 仍位于 resolved cache 内；对失败 receipt 的写入也用同一边界。

3. **[P2] cML 默认流程与 DP 变体重复。** 当前 `MR-CML` 将 `MendelianRandomization::mr_cML` 的 parameters 设 `{}`，`MR-CML-DP` 设 `{DP: true}`。本机已安装 0.10.0 的 `formals(mr_cML)$DP` 实际就是 TRUE。因此两记录默认调用相同；这不是一次独立扰动变体验证，也不应由两行推导两个不同已运行估计器。可令基线明确 `DP=false`，或把 DP 条目标为默认模式/别名。若改基线参数，需要有针对性地复核该参数组合，旧默认原生 receipt 不能当新组合证据。

4. **[P2] 同一个 IVW 记录混合了不同的少 SNP 默认方差模型。** `MR-IVW` 名为 “IVW with underdispersion correction”，同时列 TwoSampleMR `mr_ivw` 与 MendelianRandomization `mr_ivw(parameters={})`。只读本机原生实现确认：前者始终使用纠正下离散的 MRE；后者 `model="default"` 在 SNP<4 时选择 fixed，>=4 才 random。因此 2–3 SNP 且有异质性时，两默认实现的标准误可不同。现有 10 SNP 合成 receipt 不能排除此差异。可将对应 MR 包参数固定 `model="random"`，或者把默认规则写清并区分 FE 变体；原生结果应保存实际 Model，不以记录同名暗示等价。

上述两项原生默认值均通过当前已安装 API 的 formals/函数体核实，不是凭外部文档版本推测。已直接发给根代理，供其修改实现/元数据；审查代理未修代码。
